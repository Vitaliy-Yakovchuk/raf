## Причини п'яти падінь

1. `assignment uses authoritative OpenSpec argv and the configured root`: `src/assignment-identity.ts:readSource` читає перевірену копію входів і повторно використовує parse лише після перевірки digest/identity. Коміт 7b42a4faf4b3da807e184dea4e6179218bc7e109 свідомо усунув повторні CLI-виклики. Старе очікування cwd=original root і обов'язкового нового apply неправильне. Тепер тест перевіряє reuse без нових calls, відмову для чужого ID і свіжий authoritative apply після зміни tasks.md з новим description у snapshot. Аргументи apply залишені точними; cwd мусить бути окремою guarded view.
2. `compose reuses runner, stage and completion templates with the exact report path`: чинний контекст дозволяє теку `questions/projects/raf`, не один legacy `questions.md`. Коміт 2f1b9a8d303512d540a86fb1e08d0b93ad01aeb4 (`prepare project questions directory before agent sandbox launch`). Збережено всі перевірки runner/stage/completion/reportPath/tasks/cwd/rafCommand; змінено тільки адресу питань.
3. `task context is derived from parameters, OpenSpec snapshot and conf instead of a trusted file`: та сама зміна questions directory та дозволений `conf/test-runs.json` за bf2e8b6 (`allow executors to register test run groups (Z.451)`). Чинний бриф implement, абзац «Відсутні доповнення unitFiles/groups», вимагає можливість реєстрації. Збережена точна рівність writeBoundaries, перевірки FOREIGN, джерел, оцінок ресурсів, відсутності launch/claims.
4. `repainting-paste: parent handshake follows native acceptance`: synthetic runner на 400 мс показує тільки хвіст брифа без native composer. Це невідомий екран, а не доказ прийняття. Чинний `projects/raf/agent-adapters`, «Передача складеного брифа та обгортка звіту», і «Стартовий екран до готовності» не дозволяють сліпого вводу на unknown_screen; bfbdb3e6aa3633887a8bb24b812fdffb89000a26 явно відмовляє за відсутності composer. Тест тепер вимагає саме unknown_screen-відмову, відсутність accepted-файла, нуль повторних Enter та звільнення reserved-стану. Точне історичне ім'я збережено для закриття того самого knownRed ID.
5. `pending-forever: no false handshake or blind submission`: bfbdb3e6aa3633887a8bb24b812fdffb89000a26 прибрав hard timeout прийняття й лишив warning, відповідно до аудиту flow. Старе очікування `Native initial brief acceptance timed out` неправильне. Тест чекає один перевірений Enter, далі чинний transitionMs, перевіряє, що parent promise ще не завершився, контрольовано завершує synthetic runner і вимагає реальну відмову після виходу. Загальні перевірки відсутності accepted і рівно одного retry збережено. Нових production-лімітів/таймаутів не введено.

Незмінний первинний доказ усіх п'яти: `../hotfix-1.1.6/baseline-check.TestRunResult.json`, runId c8cc7272-9665-45a2-9ea1-3c64bf5ac33f, HEAD cf4d6de51269004b90cd1b8a3d38aefeb18d282f без правки 1.1.6. Власний RED та hotfix наведено у companion JSON після завершення прогонів. Точні test IDs не перейменовано; стабільна група та QA HOME не скидались.

## Самоперевірка читабельності

Область: власний diff від e4e1cf87643ea94415d19b181492f7228ff866fa у трьох callbacks production-runtime.test.ts та двох delivery callbacks production-codex-delivery-qa.test.ts. Весь зачеплений компонент переглянуто. Валідація має явні кроки reuse → invalid selection → mutation → fresh parse; усі дані локальні у fixture. Delivery має окремі явні гілки composer-less repaint і живого pending runner; єдине нове локальне значення settled змінюють лише два обробники завершення launch promise. Вихід runner задається наявними release/exitGate файлами; при збої fixture cleanup прибирає власні процеси. Одноразові доменні гілки лишено у тестах без механічних helper-обгорток. Production-функцій не додано і не змінено. `git diff --check` без помилок; поведінкові результати — у TestRunResult.
