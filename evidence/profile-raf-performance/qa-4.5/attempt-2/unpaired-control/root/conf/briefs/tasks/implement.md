# Стадія implement

Реалізуй доручені вимоги за контрактом і каркасом відповідно до core/process/feature-implementation. Не читай підготовлені тести до завершення реалізації; не підганяй їх під код.

Якщо доручено запис conf, внеси передані test-scaffold доповнення unitFiles/groups у conf/test-runs.json до прогону; інакше передай точні записи main. Після завершення незалежної початкової реалізації отримай цільовий unit-результат: `raf_command test run --project <project> --phase implement --group <change>/<unit-group> --files <file>`; наступні файли додай до того самого списку `--files`, або використовуй налаштовану групу без `--files`. Для unit-прогонів керуйся core/process/unit-test-runs і projects/raf/test-runs. Зберігай стабільну `--group <change>/<unit-group>` та агрегат переданого red між агентами, фазами, SHA й оптимізацією відбору; не перейменовуй групу й не змінюй QA HOME для скидання лічильника.

У sandbox використовуй переданий `raf_command test run` лише коли він дозволений у `raf_subcommands`, однією простою командою без env-префікса, cd, конвеєрів, підстановок чи shell-обгорток. Фаза й відбір мають відповідати авторизованому дорученню. Не обходь sandbox і не повторюй невідомий результат сліпо.

Збережи повний незмінений JSON `TestRunResult`, stderr і код CLI окремо від child exitCode. У звіті дай посилання на доказ із командою, SHA/незакоміченими змінами workspace, runId, відбором, outcome, cleanup/timeout, knownRed/unexecuted/unknown і станом групи/наступною дією; відсутній або урізаний результат не є pass.

Виконуй лише вибрані пункти з доручення. Передай результат у JSON за шляхом і схемою доручення; стан tasks.md має відповідати фактичним результатам.

Чужу unit-регресію запускай у фазі implement лише за декларацією вибраного item; правило — conf/briefs/README.md, абзац «Чужу unit-регресію».
