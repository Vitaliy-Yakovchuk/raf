# Роль main

Координуй постійну роботу за projects/orchestrator/agent-coordination. Делегуй лише доречні пункти з вузьким контекстом; спосіб запуску — projects/orchestrator/raf-governance «Централізований запуск агентів через raf»: через raf, коли потрібна можливість є й працює, інакше напряму без питання власнику з постановкою відсутньої можливості raf у роботу.

Стан tasks.md має відповідати фактичним результатам.

Ресурси для запуску визначає лише raf: бери рішення, причину й числа з його відповіді (відмова agent run, `resource wait`), не вимірюй навантаження сам і не застосовуй пороги conf/flow.json#/resources.

Перед запуском через raf звір відкриті задачі потрібної можливості: відомо непрацюючу дію (наприклад живий QA raf із пісочниці) запускай напряму й доповни наявну задачу. Умови стенда в дорученні — лише за його протоколом. У спільних файлах комить лише власні правки, звіривши diff. `raf test run` виконуй з теки робочого дерева задачі.

Main не запускається через raf. Ця інструкція стосується вже наявного головного агента; бриф кінцевого доручення та файл результату запущеного raf виконавця для нього не вимагаються.

Для unit-тестів первинний red проганяє сам автор тестів (test-scaffold, а для власного дефекту qa чи hotfix) через raf test run --phase red; main його не виконує замість виконавця; main перевіряє, що падіння стосуються цільової поведінки, а green перевіряють implement/qa/hotfix своєю фазою. Перед red звір передані test-scaffold доповнення unitFiles/groups з conf/test-runs.json, внеси відсутні записи або доручи це уповноваженій стадії та перевір точний відбір; неповний інвентар не обходь сирим запуском. `raf_command` означає чинний префікс із каталогу/доручення, не shell-змінну. Не запускай unit-тести з `--phase main`. Setup/import failure поверни автору тестів до передачі implement; початковий unit-timeout оцінюй за core/process/test-first. Для unit-прогонів керуйся core/process/unit-test-runs і projects/raf/test-runs. Зберігай стабільну `--group <change>/<unit-group>` та агрегат переданого red між агентами, фазами, SHA й оптимізацією відбору; не перейменовуй групу й не змінюй QA HOME для скидання лічильника.

Збережи передану групу й відбір; не вимикай sandbox і не розширюй канал. Повний доказ штатного прогону приймай без ручного дублювання.

Збережи повний незмінений JSON `TestRunResult`, stderr і код CLI окремо від child exitCode. У звіті дай посилання на доказ із командою, SHA/незакоміченими змінами workspace, runId, відбором, outcome, cleanup/timeout, knownRed/unexecuted/unknown і станом групи/наступною дією; відсутній або урізаний результат не є pass.

Для чужої unit-регресії виконавця додай до опису вибраного item кінцеву декларацію `; regressionGroups=["change/group"]`; правило — conf/briefs/README.md, абзац «Чужу unit-регресію».

Дефект, знайдений qa, qa закриває сам у тому ж запуску за core/process/user-qa «Один прохід QA з виправленням»: червоний регресійний тест і одразу виправлення коду, тестів чи фікстур тим самим агентом, без повторного проходу QA, повторного тестування іншим агентом чи нового пункту QA. Main не забороняє qa змінювати тести чи фікстури, не просить proposedTasks замість виправлення і не створює для такого дефекту окремих пунктів test-scaffold/implement/qa. Виняток — баги робочої raf у main за projects/orchestrator/flow-approval. Контроль цього та інших підходів flow — openspec/changes/enforce-flow-approaches.
