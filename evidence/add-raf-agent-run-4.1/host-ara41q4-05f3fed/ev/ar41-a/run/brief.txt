# Runner codex

Ця частина призначена для CLI `codex`, запущеного raf через tmux. Модель і effort уже обрані raf; не замінюй їх самостійно. Використовуй доступні інструменти цього CLI для дорученої роботи. Підсумкова відповідь у чаті не замінює JSON за `report_path` і `report_schema` з доручення. Формат запуску, доставки й продовження визначає адаптер CLI, а не текст цього брифа.


# Стадія implement

Реалізуй доручені вимоги за контрактом і каркасом відповідно до core/process/feature-implementation. Не читай підготовлені тести до завершення реалізації; не підганяй їх під код.

Якщо доручено запис conf, внеси передані test-scaffold доповнення unitFiles/groups у conf/test-runs.json до прогону; інакше передай точні записи main. Після завершення незалежної початкової реалізації отримай цільовий unit-результат: `raf_command test run --project <project> --phase implement --group <change>/<unit-group> --files <file>`; наступні файли додай до того самого списку `--files`, або використовуй налаштовану групу без `--files`. Для unit-прогонів керуйся core/process/unit-test-runs і projects/raf/test-runs. Зберігай стабільну `--group <change>/<unit-group>` та агрегат переданого red між агентами, фазами, SHA й оптимізацією відбору; не перейменовуй групу й не змінюй QA HOME для скидання лічильника.

У sandbox використовуй переданий `raf_command test run` лише коли він дозволений у `raf_subcommands`, однією простою командою без env-префікса, cd, конвеєрів, підстановок чи shell-обгорток. Фаза й відбір мають відповідати авторизованому дорученню. Не обходь sandbox і не повторюй невідомий результат сліпо.

Збережи повний незмінений JSON `TestRunResult`, stderr і код CLI окремо від child exitCode. У звіті дай посилання на доказ із командою, SHA/незакоміченими змінами workspace, runId, відбором, outcome, cleanup/timeout, knownRed/unexecuted/unknown і станом групи/наступною дією; відсутній або урізаний результат не є pass.

Виконуй лише вибрані пункти з доручення. Передай результат у JSON за шляхом і схемою доручення; стан tasks.md має відповідати фактичним результатам.

Чужу unit-регресію запускай у фазі implement лише за декларацією вибраного item; правило — conf/briefs/README.md, абзац «Чужу unit-регресію».


# Завершення доручення

Відмову чи відкладення «за рішенням власника» обґрунтовуй посиланням на чинний запис у Git із дослівною цитатою; без такого запису працюй за flow ([Відповідь та діалог](../../openspec/specs/projects/orchestrator/owner-questions/spec.md#requirement-відповідь-та-діалог)). За суперечності з нотатками чи підсумком контексту керуйся текстом нагадування/cron ([Чинний процес і джерела](../../openspec/specs/projects/orchestrator/autonomous-development/spec.md#requirement-чинний-процес-і-джерела)).

Виконавець пише й комітить власний результат і докази до JSON-звіту. Галочки саме доручених через raf --tasks пунктів tasks.md ставить і комітить raf за валідним succeeded; сам їх не змінюй. Failed не запускає відміток. Якщо це останні пункти, атомарно запиши succeeded без archive, дочекайся підтверджених галочок і комітів raf у цій самій сесії, перевір усі задачі та виконай sync/archive за projects/orchestrator/autonomous-development з урахуванням skip_specs. Закоміть власне завершення й атомарно доповни той самий JSON точним changes[].archive та власними commits. До перевірки архіву raf не приймає остаточний succeeded. Якщо інші пункти відкриті, не виконуй їх і не архівуй зміну.

Запиши JSON за report_path і report_schema з брифа. Шлях лежить у tmp-директорії конкретного запуску; назва файлу — <назва-сесії>.json. Статус бери з conf/raf-constants.json#/reportStatuses. Вкажи відповідь і результати доручених пунктів, докази та точний архів для заархівованих змін. Можеш додати інформацію про сесію. Raf звіряє виконання командами OpenSpec; текст відповіді не замінює галочок або доказів. Записуй JSON атомарно, щоб спостерігач не прийняв неповний файл.

Перед реалізацією і за нових обставин перевір актуальність та узгодженість доручених змін за вимогою аудиту в projects/orchestrator/autonomous-development. Обґрунтована відмова від суперечливої або неактуальної задачі допустима: запиши failed, поясни причини в answer та непорожньому reason кожного відхиленого пункту, назви зміни/пункти й джерела суперечності або неактуальності. Не став галочки за невиконане. Main перевіряє висновок і сам коригує чи прибирає changes.
