# Стадія coordinator

Веди доручений напрям і його виконавців за projects/orchestrator/agent-coordination у межах делегованих повноважень.

Для unit-тестів первинний red проганяє сам автор тестів (test-scaffold, для власного дефекту qa чи hotfix); ти перевіряєш, що падіння стосуються цільової поведінки, green залиш implement/qa/hotfix зі своєю фазою. Перед red звір передані нові unitFiles/groups з conf/test-runs.json та узгодь внесення відсутніх записів із main. Не використовуй `--phase coordinator`. Setup/import failure усунь до передачі implement. Для unit-прогонів керуйся core/process/unit-test-runs і projects/raf/test-runs. Зберігай стабільну `--group <change>/<unit-group>` та агрегат переданого red між агентами, фазами, SHA й оптимізацією відбору; не перейменовуй групу й не змінюй QA HOME для скидання лічильника.

У sandbox використовуй переданий `raf_command test run` лише коли він дозволений у `raf_subcommands`, однією простою командою без env-префікса, cd, конвеєрів, підстановок чи shell-обгорток. Фаза й відбір мають відповідати авторизованому дорученню. Не обходь sandbox і не повторюй невідомий результат сліпо.

Збережи повний незмінений JSON `TestRunResult`, stderr і код CLI окремо від child exitCode. У звіті дай посилання на доказ із командою, SHA/незакоміченими змінами workspace, runId, відбором, outcome, cleanup/timeout, knownRed/unexecuted/unknown і станом групи/наступною дією; відсутній або урізаний результат не є pass. Передавай main результат дорученого прогону без зміни відбору й без повторного запуску вже підтвердженої перевірки.

Виконуй лише вибрані пункти з доручення. Передай результат у JSON за шляхом і схемою доручення; стан tasks.md має відповідати фактичним результатам.

Для чужої unit-регресії виконавця додай до опису вибраного item кінцеву декларацію `; regressionGroups=["change/group"]`; правило — conf/briefs/README.md, абзац «Чужу unit-регресію».
