# Живий прохід add-raf-bug-sync:7.5

Це інструкція майбутнього проходу, не доказ успішної перевірки. Поточний результат — `failed/unexecuted`: main підтвердив, що `dash-bugs-api-for-raf-sync:6.5` ще не виконано. За останнім повідомленням main ізольований прохід також не запускався.

Після викладки 6.5 main виконує сценарій сам зі своїм secrets-store. Секрети, JWT, claim_token і сирі MCP read_bug-відповіді агенту не передавати. Зафіксувати ОС, Node, повні SHA raf-main і raf-develop, SHA Dash із health, міграцію, дату, розділ і тестовий ключ. Прохід на raf-main підтверджує raf-develop лише якщо відповідний bug-код збігається; інакше явно зазначити різницю збірок.

Використати лише спеціально виділеного тестового жука. Його статус має дозволяти реальну зміну життєвого циклу, а claim — належати raf або бути відсутнім. Не брати випадкового користувацького жука. Main визначає дозволений цільовий статус і повернення початкового статусу за чинним lifecycle; перелік статусів тут не дублюється. Потрібні початковий успішний pull і присутність тестового жука локально.

Перед блоком записів main забезпечує відсутність паралельного pull для цієї бази. Це дозволяє відрізнити синхронний локальний запис від результату фонової синхронізації. Команди нижче — для main після підготовки; цей QA-сеанс їх на реальному сервері не виконував.

```bash
RAF_QA_CLI=/srv/dev/work/orchestrator/raf-main/bin/raf.ts
RAF_QA_BUG='projects/<project>/bug#<test-number>'
RAF_QA_STATUS='<дозволений новий статус>'
RAF_QA_TEXT='<абсолютний шлях до UTF-8 файла коментаря>'

node "$RAF_QA_CLI" bug show --bug "$RAF_QA_BUG"
node "$RAF_QA_CLI" bug comment add --bug "$RAF_QA_BUG" --text-file "$RAF_QA_TEXT"
node "$RAF_QA_CLI" bug show --bug "$RAF_QA_BUG"
node "$RAF_QA_CLI" bug status set --bug "$RAF_QA_BUG" --status "$RAF_QA_STATUS"
node "$RAF_QA_CLI" bug show --bug "$RAF_QA_BUG"
```

У файлі коментаря вказати `raf-bs75-qa`, унікальну дату/мітку цього проходу й текст «Перевірка синхронного запису 7.5». Для кожної команди зберегти окремо повний stdout, stderr, CLI exit code, час початку/завершення та точні аргументи. Не повторювати запис із невідомим результатом.

Очікування після comment add: код 0, серверний `commentId`, текст і ревізія; негайний show до pull містить той самий serverId і текст рівно один раз, revision не менша за receipt. Після status set: код 0, очікуваний статус і нова ревізія; негайний show до pull має цей статус і ревізію, попередній коментар лишається. Відмова чи невідомий результат — не pass; спершу звірити серверний стан без повторної мутації.

Далі виконати реальний pull вибраного розділу. Публічної команди `bug pull` немає. Main може відновити чинний цикл служби та зберегти `bug list` до/після: для потрібного sectionId `sync.lastSuccessAt` має просунутися після записів, `snapshotComplete=true`, `lastErrorCode=null`. Саме очікування pollIntervalMs без підтвердження успішного pull не є доказом. Після підтвердженого pull виконати:

```bash
node "$RAF_QA_CLI" bug list
node "$RAF_QA_CLI" bug show --bug "$RAF_QA_BUG"
```

Main також читає свіжий detail тестового жука з Dash через свій авторизований канал і передає проєкцію без токенів: ключ, revision, status, ID/тексти коментарів. Show після pull має збігатися з цим станом; коментар з receipt — рівно один, статус не відкочується. За паралельних серверних змін повторити лише читання/pull до збігу або зафіксувати незавершеність. Зберегти стан після ще одного успішного pull для перевірки відсутності дублів.

Окремо позначити, чи справді спостерігався pull зі старішою ревізією. Звичайний послідовний живий прохід підтверджує збереження стану після pull і збіжність, але сам по собі не доводить гонку старого detail. Не підміняти живий доказ попередніми фейковими тестами.

Після проходу main повертає дозволений початковий статус лише для цього тестового жука, якщо це було передбачено підготовкою; коментар лишається як QA-мітка. Передати stdout/stderr/exit codes і серверну проєкцію виконавцю для остаточного звіту. Галочка 7.5 можлива лише після фактичного успішного проходу.
