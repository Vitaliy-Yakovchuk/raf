## Вікно CPU та підсумок

Профіль належить profile-raf-performance. Health читає атомарні знімки його агрегатів, не змінює profile rows чи EMA. Береться різниця сум user/system завершених взаємовиключних self та недубльованих helper-child інтервалів для одного початку накопичення. Дані з інтервалами поза вікном, невідомим початком, недоступним CPU чи незавершеною роботою не оголошуються повним виміром вікна. Тестами перевіряється межа інтервалів, а не припускається, що різниця довічних середніх є поточним CPU. Якщо API профілю не дає потрібної повноти, main узгоджує вузьке доповнення з його власником до реалізації health; другий збір процесних метрик заборонений.

CPU = власний cpuUserMs + cpuSystemMs за фактичний wallMs; результат — зайняті ядра. Частка helper child не включає інструментований raf child повторно, runner/model, агентський код або test payload. Нульові, відсутні й partial дані різні. Послідовні повні вікна вище порогу можуть мати окремі події; окремого порогу відновлення чи cooldown немає.

`command stats.health` розширює результат profile-raf-performance: `readAt`, `since`, `cpu` (межі, cores або null, complete/partial/unavailable, причина), `forcedClose` (completed, refusalsByCode, since), `summary` (межі, dueAt, стан доставки, delayed). Підсумок додатково має агреговані eventsByType, refusalsByCodeAndStage, queue (стан, кількість, найстаріший час/вік) та unavailable-причини для недоступних частин. Черга читається з resource-wait, без нових процесних/ресурсних вимірів. Це не друга схема TestRunResult.

Force contribution належить транзакції остаточної фіналізації поточного runId. Збереження причини до сигналу процесу ще не означає виконаного force. Результати команд і повтори одного фіналізованого runId не додають внеску. Дедуплікація спирається на чинний перехід стану; після retention зберігається агрегат, не всі runId/причини. Підсумок містить приріст completed за період і межу початку обліку.
