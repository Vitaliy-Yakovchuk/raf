# Приймання діагностики 1.2

Чинний пункт 1.2 актуальний: Mac-доказ підтверджує 19 доставок після підтверджень. Причина не встановлена: відсутні транспортні результати та state до ручного close. Linux baseline з текстом інциденту та queued/working/finished Claude не відтворює дубль. Це не RED початкового дефекту. Вказівка main: «без відтворення production-поведінку не змінюй», «мінімальну діагностику ... в state (не stdout) ... Тест на запис діагностики, коміть, звіт failed з точним запитом відтворення».

Діагностика зберігає окрему спробу до доставки, результат transport і остаточний результат settlement. Запис містить reason, receiptId, markWritten, SHA-256 кадрів до/після paste, pid, timestamps. Незавершена спроба має completedAt=null. Сирі кадри й повідомлення не зберігаються. Таблиця незалежна від видалення reminder, тому ручний close не видаляє доказ. Створюється ліниво без зміни версії основної схеми. Помилка запису діагностики не змінює результат доставки.

Самоперевірка простоти й читабельності: функція запису відповідає лише за SQLite upsert; deliverClaimedReminder об'єднує вже наявні send/confirm/release і явно фіксує їхній результат; transport observation є необов'язковим внутрішнім callback. Обгортка deliverCheckedMessage лише обчислює hashes і спостерігає результат; попередня логіка lease, прийняття та повторів збережена в deliverWithLease. State-store і production-runtime лише передають залежності. Публічний receipt, CLI, протокол Claude, часові межі та правила повтору не змінені. Дублікати settlement не додані. Функції й типи мають предметні імена, без зайвих режимів чи абстракцій.

Перевірки: diagnostic-red.json містить три assertion failures відсутнього запису перед реалізацією; final.json містить 96 passing tests, child exitCode=0, без timeout та невідомих результатів. Тести перевіряють реальну SQLite persistence, відсутність повторної доставки, pending/completed стани, accepted transport з наступною помилкою control, refusal, markWritten=false, переживання ручного close, помилку diagnostic storage та незмінний public receipt. Загальний CLI=1 через успадкований aggregate knownRed і чотири unexecuted; загальний GREEN не заявлено. npm run build і git diff --check завершилися з кодом 0. Повні результати, команди, SHA і стан workspace на момент прогонів містяться в runs.json та відповідних JSON. Після фінального прогону змінено лише докази/документні нотатки.

Точний запит наступного відтворення: main окремо активує діагностичний кандидат на Mac; після наступної повторної доставки Claude-одержувачу, до reminder close, надати вибірку `SELECT payload FROM reminder_delivery_attempts WHERE reminder_id='<id>' ORDER BY rowid;`, відповідні reminder_deliveries і delivery_claims, SHA/покоління активного raf, час повтору та результат команди/процесу. Потрібні щонайменше accepted спроба й наступний дубль одного reminder/одержувача. Це дозволить відрізнити transport refusal, втрату receipt після transport, відсутній mark і повтор після записаного mark. Повний state, секрети й сирий scrollback для цього запиту не потрібні.

Пункт 1.2 лишається failed: додано засіб встановити причину, виправлення початкового дефекту не доведено. Root tasks.md має лише допис перевірки, без галочок. Root commit відмовлено через read-only .git/index.lock; точний патч і помилку передано main. Реєстр груп змінено in-place за узгодженням; його коміт належить main.
